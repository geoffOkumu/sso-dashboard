# Deployment

## Runtime and infrastructure

Use Node.js 24, PostgreSQL 17+, a persistent identity database, and an SMTP service. Install pinned dependencies with `pnpm install --frozen-lockfile`, generate the Prisma client, run `pnpm db:migrate` as a deployment job, then build and start the central app. Run migrations once per release, not from every server instance. The configured `BETTER_AUTH_URL` must be the final public HTTPS origin, without a trailing slash. The issuer is that origin plus `/api/auth`.

The root project remains the identity app to preserve the existing starter and root database environment. Demo apps run independently from their own directories. Their tiny Node servers bind loopback by design; put a reverse proxy in front. Each owns its `.data` directory and should run as a single instance. A real horizontally scaled tool should replace demo SQLite with its own shared database; do not point it at the identity database.

Example domains:

- `https://identity.company.com`: central portal, auth routes and access API.
- `https://crm.company.com`: CRM client.
- `https://analytics.company.com`: analytics client.

Unrelated domains are supported too. No shared parent-domain cookies are used. Exact callback registration and HTTPS server-to-server reachability are required. The tools need outbound access to discovery, JWKS, token and access-check endpoints. Register a separate production client for each tool; never reuse development secrets.

## Environment and proxy

Generate a stable high-entropy `BETTER_AUTH_SECRET` using `openssl rand -base64 48`; store it in your secret manager. Do not put it in client variables. Keep production and test secrets separate. Configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, credentials and sender. For port 465 use `SMTP_SECURE=true`; for STARTTLS on 587 use `false` with SMTP credentials. Apply the provider's TLS requirements at deployment.

Terminate TLS at a trusted reverse proxy. Preserve the canonical URL and redirect HTTP to HTTPS. Strip inbound forwarding/IP headers before setting your own `X-Real-IP`, then set `TRUSTED_IP_HEADER=x-real-ip`. Do not enable arbitrary forwarded-header trust. Set request body limits (for example 64 KiB on JSON routes), idle/request timeouts and edge abuse protections. Return `Cache-Control: no-store` for all auth, personalized HTML and access APIs; never cache session responses at the CDN. The app supplies no-index, frame-denial, MIME-sniffing and referrer headers. Add HSTS at the HTTPS edge.

`GET /api/health` returns only `ok` or `unavailable` and checks database reachability. It does not expose connection strings. Configure monitoring for non-200 health responses, SMTP failure and rising authorization failures. The demos have their own `/health` endpoints.

## First administrator

Run `pnpm bootstrap` from the identity project, with access to its environment. The CLI accepts `BOOTSTRAP_EMAIL`, `BOOTSTRAP_NAME`, `BOOTSTRAP_PASSWORD`, or prompts interactively; the password prompt is hidden. Environment input is intended for a secret manager, not a shell command containing a literal password. It creates only the first administrator, never overwrites an existing account, and is idempotent for an existing active superadmin. Sign in and finish MFA enrollment before provisioning users or clients. Store recovery codes in a secure password manager.

## Keys and credential rotation

The Better Auth JWT plugin persists encrypted signing keys in `jwks`. This application configures a 30-day key rotation interval and seven-day grace period using the supported `jwks.rotationInterval` and `jwks.gracePeriod` options. New signing keys are generated by the provider; the JWKS endpoint retains keys for verification during the grace window. Do not manually generate or replace JWK cryptography. Keep the grace period longer than the maximum token lifetime and relying parties' JWKS caching. After deployment verify discovery/JWKS and a complete OIDC flow. Back up the database and encryption secret together.

Emergency signing-key compromise requires revoking active user sessions/tokens and coordinating provider-supported key retirement; signature verification alone is not revocation. Do not delete keys as a substitute for revoking sessions. For rotating `BETTER_AUTH_SECRET`, follow the pinned Better Auth version's supported secret-rotation/migration process for encrypted data; an arbitrary replacement can make stored MFA/key material unreadable. Restore-test backups before rotating encryption material.

Client-secret rotation is available in each platform's client screen. Copy the replacement once and update that tool's secret manager immediately. Client registration/rotation uses the provider's generation and hashed storage, not homemade secrets. Listing clients never returns a secret. Disabling a client denies future issuance and access checks.

## Maintenance and auditing

Run `pnpm maintenance` periodically using your deployment scheduler to remove expired rate-limit buckets and old expired verification records. Schedule is an operator choice; no workstation automation is installed by this repository. Keep audit data according to company retention requirements. Audit entries record actors, target IDs, platform IDs and selected non-secret metadata. Backups, restricted database roles, encryption at rest, log retention and SMTP deliverability are operator responsibilities.

Administrative database mutations and their audit entry commit together. Provider-managed client creation and rotation cannot share the app transaction: on failed linkage, the new client is disabled; a rotated secret cannot be read back, so repeat rotation if delivery to the administrator fails. Never log secret-bearing response bodies at a proxy.

## Limits and deliberate choices

- No refresh tokens: tool sessions expire after 15 minutes, then reauthorize through the central session. This avoids revocation being bypassed by refresh.
- Positive access checks can be cached up to 60 seconds; sensitive operations bypass cache. Central outages fail closed after cache expiry.
- Single-company scope only. No registration, tenant switching or billing.
- Demo application records and sessions use local SQLite, not a production multi-instance storage architecture.
- The Next.js starter's Turbopack CSS worker could not bind its worker port in this environment. Development and production commands use Next.js's supported Webpack option and standard Tailwind PostCSS processing.
- The pinned Next.js ESLint dependency chain includes an upstream `braces` advisory whose advisory names a fix in 3.0.4, but the configured registry currently only publishes through 3.0.3. It affects developer lint glob processing, not the production dependency tree. Do not lint attacker-controlled pathological glob configurations. Recheck and upgrade the lint chain when patched. No forced downgrade of Next.js was applied.
